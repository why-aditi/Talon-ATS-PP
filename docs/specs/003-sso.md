# Spec 003 — Google and SAML SSO, and the removal of the local provider

**Status:** draft, awaiting review gate
**Milestone:** M0b
**Depends on:** spec 001 (auth chain, §6); spec 002 work on `feat/002-cognito` (Cognito adapter, migration 0004)
**Blocks:** any customer onboarding that is not "an operator ran a script"

---

## 1. Context and goal

`feat/002-cognito` put `CognitoIdentityProvider` behind the §6.1 seam and proved it
end to end. It authenticates exactly one way: an email and a password, over
`AdminInitiateAuth`. ARCHITECTURE §9.4 specifies two more — Google as a social IdP,
and one SAML IdP per tenant that enables SSO — and spec 001 §7b.3 ships both buttons
`disabled` with copy that names the blocker.

This spec removes that blocker, and removes the local provider at the same time.

**Why the two are one spec.** They are the same decision seen twice. Once sign-in can
arrive from a redirect, "which identity provider authenticated this person" stops being
a deployment-wide constant and becomes a per-user fact. Keeping a second, wholly
different provider implementation alongside that — one that signs its own tokens and
stores its own password hashes — would mean maintaining two answers to a question that
now has to have one.

**The one-sentence job:** a person arrives at the sign-in screen, chooses Google or is
routed to their company's SAML IdP by email domain, comes back, and holds the same
§6.2 access token a password sign-in would have produced.

## 2. Scope

**In:**
- `IdentityProvider` gains a redirect-flow pair; `CognitoIdentityProvider` implements it.
- Three new public routes: SSO start, SSO exchange, domain discovery.
- Google as a pool-level social IdP.
- Per-tenant SAML: a `tenant_sso_connections` table, an admin API that creates and
  deletes the matching Cognito IdP **at runtime**, and email-domain routing.
- Removal of `LocalIdentityProvider`, `local_identities`, and `auth_user_by_email`.
- `cognito-stub.ts` promoted from test helper to the thing that makes the suite run
  without AWS, and extended to speak the OAuth endpoints.
- Spec 001 corrections listed in §12.

**Out:**
- Recovery codes (ARCHITECTURE §9.4 says ten, hashed, ours). Separate spec — they are
  an MFA feature, and MFA has no screen yet.
- TOTP enrolment. Still unimplementable behind `enrollTotp(sub)`; see §11 open question 3.
- JIT provisioning. Deliberately excluded — see §5.3.
- Account linking. Excluded by decision — see §5.2.
- IdP-initiated SAML. SP-initiated only.
- Advanced security features / adaptive auth (ARCHITECTURE §9.4). Infra, and it changes
  no contract.
- Any Terraform. `infra` owns the pool, the domain, and the Google IdP; this spec states
  what it needs from them in §4.

## 3. The decisions this spec is built on

Recorded here because each was contested and the reasoning is what a later reader needs.

### 3.1 Cognito is the only identity provider

Answered 2026-08-08. `LocalIdentityProvider` goes.

**What it costs, stated plainly so nobody rediscovers it:** spec 001 §12's definition of
done — "`docker compose up && pnpm db:migrate && pnpm db:seed && pnpm dev` yields a
working jobs list from nothing" — becomes false. From nothing plus an AWS account.

**What saves the test suite** is that `apps/api/test/cognito-stub.ts` already stubs
Cognito at the network layer rather than mocking the SDK, so `pnpm test` keeps passing
with no AWS credentials at all. That file stops being a convenience and becomes
load-bearing infrastructure: it is now the only way a developer without AWS can run
anything that boots the app. It is treated accordingly in §10 — it gets its own tests.

### 3.2 One person, one identity provider

Answered 2026-08-08: no account linking.

Cognito allocates a **different `sub` per identity provider** for the same email address.
`users.external_id` is a single globally-unique column (migration 0004) matched exactly
by `auth_user_by_sub`. So a person provisioned with a password who then signs in with
Google presents a subject that resolves to nobody.

That is the correct behaviour under this decision, and **the existing schema already
enforces it** — no migration is needed to get it. The failure must be legible, though:
§6.3 requires a distinct error rather than the generic one, because "you have an account,
but not with this button" is a different instruction from "you have no account."

### 3.3 Fail closed on an unknown person

A successful SSO sign-in for someone with no `users` row is refused. No JIT provisioning.

Auto-provisioning on email domain means whoever administers that domain's Google
Workspace can mint users inside the matching tenant. Domain control is not identity, and
tenancy is one of the five areas CLAUDE.md flags as expensive to get wrong. It is also
the reversible direction: JIT can be added later behind an explicit per-tenant flag; a
cross-tenant user cannot be un-created.

If JIT is ever added it must default the new user to `member`, which is the one role
without `comp:read`.

### 3.4 The callback lands on the web BFF, not the API

Spec 001 §7b.1 predicted this tension and guessed the other way ("an API change to set
the cookie itself — the cleaner long-term answer"). PKCE settles it the other way.

The flow needs a `state` and a `code_verifier`, and whoever *starts* the flow must
*receive* the callback to validate them. The BFF at `apps/web/src/app/api/auth/` already
starts and receives requests and already owns the httpOnly refresh cookie. Putting the
callback on the API would split that state across two origins and force the API and the
web app onto one registrable domain for the cookie to scope.

The API therefore stays a pure JSON API and gains no cookie handling.

### 3.5 `state` is a signed token, not a row and not a Redis key

The API must carry `code_verifier` and `nonce` from the start of the flow to the
exchange. Three options were considered:

- **A row** (`sso_login_attempts`) — a table whose only job is to be written and deleted
  seconds later, plus a reaper for the ones nobody comes back for.
- **Redis** — already in docker-compose and ARCHITECTURE, but not yet in the api request
  path at all. Adding that dependency for one feature is a bigger step than the feature.
- **A signed, short-lived token** — chosen. `state` is an HS256 JWT signed with
  `TALON_JWT_SECRET`, `aud: talon-sso-state`, 10-minute expiry, carrying
  `{ code_verifier, nonce, connection, redirect_uri }`.

**The trade, honestly:** a signed state is replayable within its 10 minutes, where a
deleted row would not be. It buys nothing an attacker wants: the authorization **code**
is single-use at Cognito, so a replayed state with a spent code fails at the token
endpoint, and a replayed state with no code is not a credential. The CSRF protection
comes from the BFF's cookie binding (§6.2), which is where it belongs.

Distinct `aud` again, for the same reason the refresh token has one: a state token must
never be presentable as a bearer token.

## 5. Data model changes

### 5.1 `tenant_sso_connections` (new)

A tenant's SAML configuration. Google needs no row — it is pool-level and available to
every tenant.

```sql
create table tenant_sso_connections (
  id uuid primary key,
  tenant_id uuid not null references tenants (id),
  -- The Cognito IdP name inside the pool. Created at runtime by the admin API
  -- (ARCHITECTURE §9.4: these are tenant data, not infrastructure — Terraform
  -- managing them would make customer onboarding a deploy).
  cognito_idp_name text not null unique,
  -- Routes /authorize by domain. Set as the IdP's IdpIdentifier in Cognito.
  --
  -- GLOBALLY unique, not unique per tenant, and for the same reason users.email
  -- and users.external_id are (migration 0004): discovery runs BEFORE
  -- app.tenant_id exists, so a per-tenant constraint would let two tenants claim
  -- one domain and leave the lookup ambiguous — a cross-tenant identity
  -- confusion, not a data-quality problem.
  email_domain citext not null unique,
  -- Display name for the sign-in screen ("Acme SSO"). Never the tenant name:
  -- discovery is unauthenticated (§6.4).
  label text not null,
  status text not null check (status in ('pending', 'active', 'disabled')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (tenant_id, id)
);
create index tenant_sso_connections_tenant_idx on tenant_sso_connections (tenant_id);

alter table tenant_sso_connections enable row level security;
alter table tenant_sso_connections force row level security;
create policy tenant_isolation on tenant_sso_connections
  using (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  with check (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
```

`email_domain` is `citext` — domains are case-insensitive by RFC, unlike
`users.external_id`, which is `text` precisely because an IdP subject is an opaque
case-sensitive string. The two columns look similar and must not be given the same type
by analogy.

**A `security definer` reader, exactly as §11b required for `users`.** Discovery runs
before any tenant context exists, so it has the same bootstrap problem and takes the same
answer — a function granted a *result*, not a connection granted a *table*:

```sql
create function auth_sso_connection_by_domain(p_domain citext)
returns table (id uuid, tenant_id uuid, cognito_idp_name text, label text, status text)
language sql stable security definer set search_path = pg_catalog, public
as $$
  select c.id, c.tenant_id, c.cognito_idp_name, c.label, c.status
  from public.tenant_sso_connections c
  where c.email_domain = p_domain and c.status = 'active';
$$;
revoke all on function auth_sso_connection_by_domain(citext) from public;
grant execute on function auth_sso_connection_by_domain(citext) to talon_app;
```

Filtering `status = 'active'` **inside** the function, not at the call site: a `pending`
connection is one whose Cognito IdP may not exist yet, and routing a sign-in at it
produces an error page from Cognito rather than from us.

**Rollback:** `drop function`, `drop table`. No backfill — the table starts empty and
every row is created through the admin API.

### 5.2 Removing the local provider

```sql
drop function auth_user_by_email(citext);
drop table local_identities;
```

**Rollback:** re-run `0003_local_identities.up.sql`. Password hashes are not recoverable,
which is correct — they are credentials, not data, and their loss is the point.

**Ordering:** this migration must land **after** every environment has re-provisioned
against Cognito (`pnpm --filter api seed:identities`), because until then
`users.external_id` is null for everyone and dropping the local path locks all of them
out. A migration cannot check that. §9 edge case 12 covers what it looks like if it
happens anyway.

## 6. API contract

All new Zod schemas live in `packages/contracts`. No response shape is declared inline in
a route, and no OpenAPI fragment is hand-written.

### 6.1 The seam

```ts
export interface SsoConnectionRef {
  /** 'google' | a tenant connection id */
  kind: 'google' | 'saml';
  /** Cognito IdP name. 'Google' for the social provider. */
  idpName: string;
}

export interface AuthorizationRequest {
  authorizationUrl: string;
  /** Opaque to the caller. Signed; see §3.5. */
  state: string;
}

export interface IdentityProvider {
  // ... the six from spec 001 §6.1 + the step-4 refresh addition
  beginSso(input: {
    connection: SsoConnectionRef;
    redirectUri: string;
  }): Promise<AuthorizationRequest>;

  completeSso(input: {
    code: string;
    state: string;
  }): Promise<AuthResult>;
}
```

`beginSso` is not `authorizationUrl()` returning a string: the state must be minted by
whoever will validate it, and returning the two together makes it impossible to build a
URL and forget the state.

**`LocalIdentityProvider` does not need an answer for these**, because it ceases to
exist. That is the second reason §3.1 and the SSO work are one spec: had local survived,
these two methods would have needed a "this provider cannot" branch on the *sign-in*
path, which is a far worse place for one than `enrollTotp`.

### 6.2 Routes

All three are **public** — you cannot present a token to the endpoint that issues one.
Each is registered in `apps/api/src/modules/identity/routes.ts` (reached via
`public-routes.ts`, which carries no auth hooks) **and** added to `PUBLIC_ROUTES` in
`apps/api/src/route-manifest.ts`. Both, deliberately: the manifest test fails otherwise,
and that failure is the feature.

```
POST /v1/auth/sso/start
  → { connection: { kind: 'google' } | { kind: 'saml', connectionId: uuid } }
  ← 200 { authorizationUrl: string, state: string }
  ← 404 urn:talon:error:sso-not-configured   (unknown or non-active connection)
```

The BFF stores `state` in a short-lived httpOnly cookie and 302s the browser to
`authorizationUrl`. **404, not 400, for an unknown connection** — the same reason a
cross-tenant resource is 404: a 400 distinguishing "no such connection" from "connection
disabled" tells an unauthenticated caller which companies use Talon.

```
POST /v1/auth/sso/exchange
  → { code: string, state: string }
  ← 200 SignInResponse            (identical shape to POST /v1/auth/sign-in)
  ← 401 urn:talon:error:sso-state-invalid       (expired, wrong aud, bad signature)
  ← 401 urn:talon:error:sso-exchange-failed     (Cognito refused the code)
  ← 401 urn:talon:error:user-not-provisioned    (authenticated, nobody to be)
  ← 401 urn:talon:error:sso-wrong-method        (§3.2 — right person, wrong button)
```

The BFF calls this **after** checking its cookie state equals the query state. The API
checks the signature and expiry independently; neither check substitutes for the other.

`SignInResponse` is reused unchanged. The whole point of §6.2's claim shape is that the
client cannot tell how the person authenticated.

```
GET /v1/auth/sso/discover?email=<address>
  ← 200 { method: 'password' }
      | { method: 'sso', connection: { kind, connectionId?, label } }
```

Never 404, never an error for an unknown address, and never the tenant name — only the
`label`. Always 200 with `method: 'password'` when nothing matches, so the response is
identical for "no such domain" and "domain with no SSO". An unauthenticated endpoint that
answers "is this an account?" differently is an enumeration oracle, and this one is
reachable by anyone who can load the sign-in page.

**Rate limited** at the edge (WAF, stricter rule on `/v1/auth/*` per ARCHITECTURE §9.4)
and by IP in-process. It is the only endpoint here that takes an arbitrary email.

### 6.3 Admin routes (authenticated, `admin` only)

Registered **inside** the authenticated scope — no per-route hooks, ever.

```
GET    /v1/sso-connections            ← 200 { data: SsoConnection[] }
POST   /v1/sso-connections            → { emailDomain, label, metadataUrl | metadataXml }
                                      ← 201 SsoConnection
DELETE /v1/sso-connections/:id        ← 204
```

`POST` creates the Cognito IdP *and* the row. Ordering and failure handling in §9 edge
cases 6 and 7. Accepts `Idempotency-Key`; writes return the full resource including
`version`; every mutation writes `audit_log` with actor, before, after, IP, request id.

The domain uniqueness constraint is global, so a second tenant claiming a taken domain
gets **409** with `urn:talon:error:domain-already-claimed` — and deliberately no
indication of who holds it.

### 6.4 New error types in `packages/contracts`

`SSO_NOT_CONFIGURED`, `SSO_STATE_INVALID`, `SSO_EXCHANGE_FAILED`, `SSO_WRONG_METHOD`,
`DOMAIN_ALREADY_CLAIMED`. Stable `type` values; the UI switches on `type`, never status.

## 7. UI spec

`ui` owns this and the exact tokens; recorded here so the streams build against one shape.
Spec 001 §7b.3 currently renders Google and SAML `disabled` with copy naming the blocker —
that copy comes out, and the buttons become real.

| State | Behaviour |
|---|---|
| Default | Google button enabled. SAML button reads "Continue with SSO" and opens the email-first flow |
| Email entered, discovery says `sso` | Password field hides; primary CTA becomes "Continue with {label}" |
| Email entered, discovery says `password` | Unchanged from spec 001 §7b |
| Redirecting | Button shows a spinner and is disabled; the tab is leaving, so no skeleton |
| Returned, exchanging | Full-page state — the browser has navigated, there is no form to overlay |
| `sso-wrong-method` | "This account signs in with {other method}." Names the fix, per spec 001 §7b.3's rule that copy names the real blocker and the next move |
| `user-not-provisioned` | "Your sign-in worked, but you don't have a Talon account yet. Ask an admin to invite you." Explicitly not "invalid credentials" — they were valid |
| `sso-exchange-failed` / `sso-state-invalid` | "That sign-in link expired. Try again." + a retry that restarts the flow |
| Callback carries `?error=access_denied` | User cancelled at the IdP. Return to sign-in with no error styling — cancelling is not a failure |

Keyboard: the whole flow must be walkable without a mouse, including the return leg.
`axe` clean. No color-only status.

## 8. Permissions

| Action | admin | recruiter | hiring_manager | member |
|---|---|---|---|---|
| Sign in via SSO | ✓ | ✓ | ✓ | ✓ |
| `GET /v1/sso-connections` | ✓ | — | — | — |
| `POST` / `DELETE` | ✓ | — | — | — |

Enforced in `service.ts`, never in a component. No comp fields appear anywhere in this
spec's payloads; the `comp:read` scope is untouched.

Deleting a connection does **not** sign its users out. `tokens_valid_after` exists for
that and is a separate, deliberate act — see §9 edge case 9.

## 9. Edge cases

1. **State expired** (>10 min at the IdP) → 401 `sso-state-invalid`, UI offers retry.
2. **State replayed with a spent code** → Cognito refuses the code → 401
   `sso-exchange-failed`. This is the case §3.5 accepts by design.
3. **State signature valid, `aud` is `talon-api`** → refused. A bearer token must never
   be usable as a state token or the reverse.
4. **Cookie state ≠ query state** → the BFF rejects before calling the API. CSRF on the
   callback.
5. **Google returns `email_verified: false`** → refused. An unverified email is not an
   identity, and `users.email` is the join.
6. **SAML IdP created in Cognito, row insert fails** → orphan IdP in the pool. The
   service creates the row **first** in status `pending`, then the IdP, then flips to
   `active`; a `pending` row older than an hour is a reconciliation target, and
   `auth_sso_connection_by_domain` never routes at one.
7. **Row deleted, Cognito IdP delete fails** → transaction rolls back, row stays. Better
   an undeleted connection than a row pointing at nothing.
8. **Two tenants claim one email domain** → 409 at the second. §5.1's global uniqueness.
9. **User disabled at the IdP mid-session** → their access token stays valid for up to an
   hour. This is the same window as spec 002's refresh design and is why the refresh
   token is Cognito's. Immediate revocation is `tokens_valid_after`.
10. **Person has a password, clicks Google** → 401 `sso-wrong-method` (§3.2), not
    `user-not-provisioned`. Different instruction.
11. **SAML assertion carries no email** → 401 `sso-exchange-failed`. Nothing to join on.
12. **`local_identities` dropped before an environment re-provisioned** → every user is
    locked out with `user-not-provisioned`, recoverable only by running
    `seed:identities`. §5.2 states the ordering; nothing enforces it, which is why it is
    an edge case and not a footnote.
13. **Clock skew on the state token** → same policy as everything else: 60s leeway on
    `exp`, bounded leeway on a future `iat`. Spec 002 learned this the expensive way
    against a real pool.
14. **Discovery on a malformed email** → 200 `{ method: 'password' }`. Never a validation
    error: a 400 for "not an email" and a 200 for "email, no SSO" is an oracle.
15. **Tenant deleted with an active connection** → connection rows cascade; the Cognito
    IdP is deleted by the same service path, not left behind.

## 10. Test plan

Keyed to the acceptance criteria in §11.

| Layer | Covers |
|---|---|
| Unit | State token mint/verify incl. `aud` confusion and skew; discovery domain parsing; the `sso-wrong-method` decision |
| Integration (network-stubbed Cognito) | Full start→exchange round trip; every §9 edge case that has an API-observable result; `tenant_sso_connections` RLS; admin create/delete incl. the ordering in edge cases 6 and 7 |
| **`cognito-stub.ts` itself** | It now gates the whole suite (§3.1). It gets tests: that it refuses an unexpected URL, that its error shape actually deserialises into a named SDK error, that its OAuth endpoints reject a bad verifier |
| Isolation | Admin routes as a hostile tenant → 404. Discovery asserted to leak nothing across tenants |
| Route manifest | The three public routes present in `PUBLIC_ROUTES`; the three admin routes absent from it |
| Contract | OpenAPI snapshot |
| E2E | Google sign-in; SAML sign-in by domain; cancel at IdP; wrong-method; unprovisioned |
| a11y | `axe` on sign-in in all states in §7 |

**The E2E flow named in spec 001 §10 — "sign in with the local provider" — must be
rewritten in this spec's PR**, not left pointing at something deleted. Note there is
still no `e2e` script in the root `package.json`; that gate is declared and missing, and
CLAUDE.md §8 says a named-but-missing gate cannot be a required check.

**Third-party stubbing:** Google and the SAML IdP are stubbed at the network layer with
route interception, like Cognito. A nightly job runs the same flows against real sandbox
credentials — that is where a real Google consent screen gets exercised, not in CI.

## 11. Acceptance criteria

1. A seeded user signs in with Google end to end and receives a §6.2 access token whose
   `tenant_id` and `role` come from `users`, demonstrated by changing the role in the
   database between two sign-ins.
2. A seeded user in a tenant with a SAML connection is routed by email domain, signs in,
   and receives the same claim shape. Decoded claims from a Google and a SAML sign-in
   shown side by side: identical but for `sub`.
3. `GET /v1/jobs` with an SSO-issued token returns the six-job table; a `member` gets no
   `band` key, a `recruiter` does.
4. A person provisioned for password sign-in who clicks Google gets `sso-wrong-method`,
   not a token and not a generic failure.
5. An admin creates a SAML connection through the API, the Cognito IdP appears in the
   pool, a user on that domain signs in, the admin deletes it, and the IdP is gone.
6. `pnpm test`, `pnpm test:routes`, `pnpm test:isolation` pass **with no AWS credentials
   and no AWS config file**, as spec 002's suite already does.
7. `LocalIdentityProvider`, `local_identities` and `auth_user_by_email` are gone, and
   nothing in the tree references them.
8. Every §9 edge case has a test or a written reason it does not.

## 13. Open questions

1. **Does an admin choose a user's sign-in method, or does the domain?** §3.2 makes each
   person single-method, but nothing yet decides *which*. If a tenant enables SAML, do its
   existing password users migrate, and how? This blocks the admin UI, not the API.
   **Owner: Aditi.**
2. **Does Google need a domain allow-list?** Today any Google account whose email matches
   a `users` row can sign in. That is fail-closed and probably right, but it means a
   personal Gmail matching a work address works. **Owner: Aditi.**
3. **TOTP enrolment remains unimplementable** behind `enrollTotp(sub)` — Cognito's is
   session-scoped. Either the interface changes or MFA gets its own exchange.
   **Owner: api**, deferred to the MFA spec.
4. **Rate limiting has no home.** §6.4 assumes WAF plus in-process; neither exists.
   **Owner: infra.**
